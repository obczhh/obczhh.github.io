Host头注入-实战利用-ai

Nginx Host头注入 + SSRF 攻击云元数据服务：从Web到Shell的完整渗透

摘要: 本文详细记录了一次针对部署在云环境中的Web应用的渗透测试过程。通过发现Nginx反向代理配置中的Host头注入漏洞，结合SSRF技术访问云厂商实例元数据服务（IMDS），最终从User-Data中获取服务器SSH登录凭证，实现从Web应用到服务器Shell的完整攻击链。本文旨在帮助安全从业者理解此类漏洞的原理与危害，并提供修复建议。

### 各家云厂商的元数据服务地址

云厂商 元数据服务地址 说明
AWS 169.254.169.254 AWS EC2 实例元数据服务
GCP 169.254.169.254 + metadata.google.internal Google Cloud 元数据服务
Azure 169.254.169.254 Azure 实例元数据服务（IMDS）
阿里云 100.100.100.200 阿里云 ECS 元数据服务
腾讯云 metadata.tencentyun.com 腾讯云元数据服务
华为云 169.254.169.254 华为云元数据服务

这个地址为什么是通用的？

169.254.0.0/16 是 IANA 保留的链路本地地址段（RFC 3927），云厂商选择 169.254.169.254 作为元数据服务端点，是因为：

  1. 它不是公网IP，不会被外部路由
  2. 它不会与内部网络冲突，因为链路本地地址段在本地网络内有效
  3. 所有主流云厂商都使用它（AWS最早使用，其他厂商跟进）

1. 引言

在云原生时代，越来越多的应用部署在云服务器上。云厂商为每台云服务器提供了一个特殊的实例元数据服务（Instance Metadata Service, IMDS），运行在 169.254.169.254 这个链路本地地址上。通过这个服务，实例可以获取自身的主机名、网络配置、IAM角色凭证等信息。

然而，当Web应用的反向代理（如Nginx）配置不当时，攻击者可以通过Host头注入或SSRF技术，强制服务端向 169.254.169.254 发起请求，从而窃取云实例的敏感数据。本文将完整复现这一攻击链路。

2. 漏洞原理深度解析

2.1 Host头注入（Host Header Injection）

2.1.1 HTTP Host头的角色

HTTP/1.1 规范（RFC 7230）要求每个请求必须携带 Host 头，用于指定目标主机名和端口号。这使得同一台服务器可以托管多个域名（虚拟主机）。

2.1.2 Nginx中的Host头处理

Nginx 在处理请求时，有几个与Host相关的变量：

变量 来源 说明
$host 请求行或Host头 不含端口号，已规范化
$http_host 原始Host头 含端口号，未处理
$server_name nginx配置 当前server块的server_name

关键问题：当Nginx配置中使用 $http_host 或 $host 作为 proxy_pass 的目标地址时，攻击者可以通过篡改Host头来控制Nginx将请求转发到任意地址。

2.2 云实例元数据服务（IMDS）

2.2.1 什么是IMDS？

云厂商为每台云服务器提供了一个内置的HTTP服务，运行在特殊的链路本地地址上。实例可以通过这个服务获取自身的配置信息和临时凭证。

AWS EC2 元数据服务：

  • 地址：http://169.254.169.254/
  • 路径：/latest/meta-data/（实例元数据）、/latest/user-data/（用户自定义数据）
  • 版本：支持 IMDSv1（直接请求）和 IMDSv2（需要会话Token）

为什么是 169.254.169.254？

  • 169.254.0.0/16 是 IANA 保留的链路本地地址段（RFC 3927）
  • 该地址段不会在公网路由，也不会与内部网络冲突
  • AWS 最早使用此地址，GCP、Azure、华为云等主流厂商均沿用

2.2.2 IMDS能获取到什么？

路径 内容 敏感程度
/latest/meta-data/ 元数据键列表 低
/latest/meta-data/instance-id 实例ID 低
/latest/meta-data/public-ipv4 公网IP 低
/latest/meta-data/iam/security-credentials/ IAM角色凭证 🔴极高
/latest/user-data 用户启动脚本 🔴极高
/latest/dynamic/instance-identity/document 实例身份文档 中

2.2.3 User-Data的风险

User-Data 是用户在创建云服务器时传入的初始化脚本，常用于：

  • 安装软件包
  • 配置服务
  • 设置初始密码（高危！）
  • 下载并执行远程脚本

2.3 SSRF（服务端请求伪造）

SSRF（Server-Side Request Forgery）是指攻击者通过操纵服务端发起请求，访问内网或本应受限的资源。

Host头注入本质上就是一种SSRF——攻击者通过篡改请求头，让Nginx这个”中间人”替自己向目标地址发起请求。

6. 漏洞根因分析

6.1 Nginx配置缺陷

问题所在：

  1. $http_host 直接来自客户端请求，完全可控
  2. 没有对Host头做任何校验或白名单
  3. 允许代理到任意地址，包括链路本地地址

6.2 云安全配置缺陷

  1. 使用IMDSv1（而非更安全的IMDSv2）
  2. User-Data中包含明文密码
  3. IAM角色权限过大
  4. 多因素认证未启用

7. IMDSv1 vs IMDSv2

7.1 IMDSv1（有缺陷的版本）

IMDSv1 是简单的HTTP请求，没有任何保护机制：

缺陷：任何能发起HTTP请求的进程/漏洞都可以访问元数据。

7.2 IMDSv2（增强版本）

IMDSv2 引入了基于会话的Token机制：

保护机制：

  1. Token必须通过 PUT 请求获取（SSRF通常只能发 GET）
  2. Token有有效期（TTL）
  3. 需要特定的请求头 X-aws-ec2-metadata-token-ttl-seconds

8. 修复建议

8.1 紧急修复（立即执行）

  1. 轮换所有泄露的凭证

    • 更改服务器root密码
    • 轮换AWS IAM凭证
    • 轮换阿里云AK/SK
    • 撤销GitHub Personal Access Token

  2. 修复Nginx配置

  3. 启用IMDSv2

8.2 长期修复

  1. Nginx安全加固

    • 校验Host头白名单
    • 使用 $server_name 而非 $http_host
    • 配置 proxy_pass 使用固定地址

  2. 云安全加固

    • 启用IMDSv2
    • 不要在User-Data中存储敏感信息
    • 使用AWS Secrets Manager管理密码
    • IAM角色遵循最小权限原则

  3. 监控与检测

    • 监控对 169.254.169.254 的异常请求
    • 配置WAF规则拦截Host头篡改
    • 启用CloudTrail记录元数据访问

10. 总结

本文详细记录了一次从Web应用到服务器Shell的完整渗透过程。攻击者通过以下步骤实现了攻击：

  1. 发现：信息收集发现Nginx反向代理配置
  2. 突破：Host头注入漏洞允许访问AWS元数据服务
  3. 提取：从User-Data中获取SSH密码
  4. 控制：SSH登录获得服务器root权限

核心教训：

  • Nginx配置中的 $http_host 变量是危险源，不应直接用于路由
  • 云元数据服务是SSRF攻击的高价值目标
  • User-Data不应包含任何敏感信息
  • IMDSv2 应作为云服务器的默认配置

这个案例再次证明，安全配置的疏忽和云服务的错误使用，可能导致从一个小小的Web漏洞演变为整个云基础设施的沦陷。
